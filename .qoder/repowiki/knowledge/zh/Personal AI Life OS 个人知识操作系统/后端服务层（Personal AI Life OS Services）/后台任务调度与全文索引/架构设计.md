模块由三个职责清晰的子文件组成：
- `jobs.py`：定义持久化任务队列的核心抽象——通过 `BackgroundJob` ORM 模型 + `enqueue_background_job()` 入队（按 `dedupe_key` 去重，支持已完成状态的重入），使用 `_current_claim()` 实现分布式锁式的 `claim_id` 租赁机制，并通过 `_execute_photo_ocr` / `_execute_photo_description` / `_execute_weekly_review` 等钩子方法分发不同 `kind`；对外暴露取消入口如 `cancel_jobs_for_source`、`cancel_model_jobs_for_owner`。
- `scheduling.py`：基于本地 `datetime`+`zoneinfo` 的轻量轮询器（`SCHEDULE_POLL_INTERVAL_SECONDS=30`，每次最多处理 `MAX_DUE_SCHEDULES_PER_RUN=20` 条）计算下次运行时间并构造 ReviewSchedule 触发项；对于已配置外部模型的场景，先在调度器端做预算/同意校验，再通过 `enqueue_background_job` 将实际的 LLM 调用推入 `jobs.py` 的工作队列。
- `search_index.py`：负责按数据库方言自动创建搜索后端——SQLite 走 FTS5 trigram 虚拟表及 INSERT/UPDATE/DELETE 触发器维护增量同步；PostgreSQL 则启用 `pg_trgm` 扩展并建 GIN 索引。`rebuild_search_index()` 用于全量重建，`fts_candidate_filter()` 把匹配结果以 SQL IN 子句注入到上层查询中，兜底走 LIKE 回退。

依赖方向单向：`scheduling → jobs`；三者均仅向下依赖 `models/config/parsers/storage/services.model_providers` 等上层服务，不反向被业务路由直接耦合（仅通过函数式 API 被引用）。所有副作用（写入 DB、调用 LLM、读对象存储）均包裹在 SQLAlchemy Session 事务内，异常统一转为 `RetryableJobError` 以便队列重试。
